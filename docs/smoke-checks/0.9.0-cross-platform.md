# 0.9.0 cross-platform smoke checks

Two cross-platform fixes shipped in 0.9.0; both need a real machine of the
target OS to verify since their guards are platform-conditional.

## 1. Windows argv length cap (≈32 KB) → stdin fallback

**Why:** Windows' `CreateProcessW` rejects command lines longer than ~32K
UTF-16 characters. A pasted long note in the composer can exceed that and
crash spawn with `E2BIG` / `ERROR_FILENAME_EXCED_RANGE`. Fix: when the prompt
exceeds 20 KB UTF-8 bytes on Windows, pass `-p` with no positional argument
and pipe the prompt to the CLI's stdin instead.

**Implementation pointer:** `shouldSendPromptViaStdin(promptByteLength, platform)`
in [src/cli/runner.ts](../../src/cli/runner.ts); threshold constant
`PROMPT_VIA_STDIN_THRESHOLD_BYTES` in [src/constants.ts](../../src/constants.ts).
On macOS/Linux the helper always returns `false`, so behavior there is
unchanged from 0.8.2.

### Windows checklist

- [ ] **Short prompt golden path.** Send a normal "hello" message. Confirm
  the assistant replies. (Stdin path is *not* taken — sanity check that the
  default code path still works.)
- [ ] **Threshold prompt.** Paste roughly 25 KB of text into the composer
  (a long note works fine) and send. Expected: assistant processes the
  prompt normally, no spawn error in dev console / Diagnostics panel.
- [ ] **Very large prompt.** Paste roughly 200 KB of text. Expected: still
  works (stdin is not bounded by argv limits).
- [ ] **Verbose log line.** With Verbose logging enabled in settings, the
  log line for the spawn should now include `promptViaStdin: true` for the
  large prompts and `false` for short ones.
- [ ] **Resume + large prompt.** Send a large prompt to an existing session
  (so `--resume` is in argv). Expected: works; verify session continuity.
- [ ] **Abort.** Start a large-prompt turn and click Stop. Expected: child
  exits within ~2s, no zombies in Task Manager.
- [ ] **Non-ASCII content.** Paste 25 KB of CJK text (each char is 3 UTF-8
  bytes, so byte-length triggers stdin even though char count is lower).
  Expected: works.

### Linux checklist

The fallback never triggers on Linux — but Linux is the second untested
target overall, so this is also the moment to do a baseline pass.

- [ ] **Bundled CLI installs and runs.** `linux-x64` glibc and (separately)
  `linux-x64-musl` if you have an Alpine box.
- [ ] **Short prompt + tool use.** Read/Grep/Edit lifecycle.
- [ ] **Permission prompt.** Triggers correctly via the hook IPC.
- [ ] **Large prompt (25 KB).** Should work via the *default* (positional)
  path on Linux — argv limits are >256 KB. If the spawn fails on Linux
  this is a separate bug, not the Windows fix.

## 2. Stale `claude.prev.exe` cleanup on Windows

**Why:** During an in-place upgrade we rename the current `claude.exe` to
`claude.prev.exe` before swapping in the new binary. If Obsidian is running
when an install fails partway, the `.prev.exe` file may be locked and stay
on disk until next reboot. Fix: on every plugin load and at the start of
`ensureBinary`, sweep any `claude.prev.exe` older than 24h. Locked-file
errors (`EBUSY` / `EPERM`) are swallowed silently.

**Implementation pointer:** `cleanupStaleArtifacts()` (public) and
`cleanupStalePreviousBinary()` (private) in
[src/binary/installer.ts](../../src/binary/installer.ts); helper
`shouldRemoveStalePreviousBinary(ageMs, thresholdMs)` is unit-tested.
`STALE_PREVIOUS_BINARY_AGE_MS = 24h` lives in
[src/constants.ts](../../src/constants.ts). Cleanup is called from both
`main.ts:onload` and from `BinaryInstaller.ensureBinary`.

### Windows checklist

- [ ] **Setup: simulate a stale leftover.**
  1. Install the plugin and let it download `claude.exe` once.
  2. Quit Obsidian.
  3. Open `<vault>/.obsidian/plugins/claude-code/bin/`.
  4. Copy `claude.exe` to `claude.prev.exe`.
  5. Backdate the `.prev.exe` file's mtime more than 24h: in PowerShell —
     `(Get-Item claude.prev.exe).LastWriteTime = (Get-Date).AddDays(-2)`.
- [ ] **Stale file is removed on plugin load.** Reopen Obsidian. Expected:
  `claude.prev.exe` is gone within a second of the plugin loading.
- [ ] **Fresh file is preserved.** Repeat the setup but skip the backdate
  step (file is younger than 24h). Reload Obsidian. Expected: file remains
  on disk.
- [ ] **Locked file is left alone (no crash).** Repeat the setup, but while
  Obsidian is closed open `claude.prev.exe` in another process that holds
  a lock (e.g. `Get-Content claude.prev.exe -Wait` in PowerShell). Reopen
  Obsidian. Expected: plugin loads cleanly; the file is still on disk;
  the dev console has at most a debug warning, no error toast.
- [ ] **Upgrade flow still works end-to-end.** With the cleanup logic
  present, perform a normal update via Settings → Update. Expected: the
  upgrade still produces a `.prev.exe`, the new binary self-checks, and a
  subsequent reload (or 24h+ wait) prunes the leftover.

### Linux checklist

Cleanup is gated by `isWindows()` and is a no-op on Linux. Quick sanity
check only:

- [ ] **No-op on Linux.** Touch a fake `claude.prev` in the bin dir, set
  its mtime to 30 days ago, reload Obsidian. Expected: file remains
  untouched (Linux doesn't suffer from the lock issue, so we leave the
  file alone there to avoid masking any in-flight install state).

## What's *not* covered by this batch

- The full cross-platform smoke list from `TODO.md` ("macOS x64, Linux glibc
  x64, Linux musl, Windows x64") — this batch only addresses the two
  platform-specific bugs. The first-time install flow on each OS still needs
  exercising end-to-end.
- The `PROMPT_VIA_STDIN_THRESHOLD_BYTES` value (20 KB) is conservative; if
  a real-world Windows user reports overflow under that, lower it. There is
  no failure mode from lowering it — stdin path is functionally equivalent
  to argv path.

## Reporting back

If anything fails, please capture:
1. Output of `claude --version` (the bundled binary path is in Settings).
2. Last ~50 lines of the plugin's Diagnostics panel.
3. Dev console messages tagged `[claude-code]` around the failure window.
